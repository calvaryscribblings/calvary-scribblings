## §0 — WHAT HAS CHANGED SINCE HANDOVER 1

Five weeks, and the picture is better in one specific way and unchanged in another.

**Six of the thirteen launch-blockers are closed.** `39b908c` closed LB-2 (private DMs).
`f8f547d` closed LB-3, LB-4, LB-5, LB-6 and the `stories` half of LB-1. Not by the platform
workstream — by the bookstore round that could not wait — but closed, deployed, and now held in
place by a test.

**There is now CI in front of the rules file, which there was not.**
`.github/workflows/rules-and-hygiene.yml` (added `9403a18`, fixed `2fa4475`) runs three jobs:

- **`rules`** — a hermetic Firebase-emulator suite, `tests/rules/**`, **111 assertions**, on every
  push, no secret required. This is the one that matters to you: it asserts what the rules
  **allow and deny**, so a permissive edit fails CI instead of shipping.
- **`drift`** — `npm run rules:check`, repo === live, on a real service-account secret which is
  now set and genuinely running.
- **`hygiene`** — the newsletter suites, a lint ratchet, `npm audit`, and (as of R9.2) a workflow
  self-check.

**What this means for you, concretely:** a fix you write for anything below gets a probe in
`tests/rules/database.test.mjs`, and `npm run test:rules` tells you in ~20 seconds whether it
works, against an emulator, with no credential and no production data. That was the missing
tool. The four-case template at the head of that file (`unauthenticated · stranger · WIPE ·
THE LEGITIMATE WRITE`) is worth reading before you write the first one — the fourth case has
already caught two rules that would have shipped broken.

**Nothing on the PRE-LAUNCH list has been actioned.** All six items below stand exactly as
handed over. Two are single commands.

## §1 — THE ONE THAT GOT WORSE: LB-1 IS HALF-CLOSED

### PH2-1 · `top_stories` is still writable by anyone on the internet — **LAUNCH-BLOCKING**

```json
"top_stories": { ".read": true, ".write": true }
```
`database.rules.json:12-15`. No `auth` clause, no `.validate`, no size bound.

`stories` — its twin, and the other half of R9.0 LB-1 — was set to `".write": false` in
`f8f547d` and is fine. `top_stories` was left open **deliberately and for a good reason**, which
`tests/rules/structure.test.mjs:69-76` states in full:

> *"R9.0: deliberately NOT closed. `.write` is true (unauthenticated) and `top_stories/weekly` is
> regenerated on a schedule by something that is not in this repo, so locking it blind risks
> silently killing a live daily job. Needs the writer identified before it can be closed.
> REMOVE THIS ENTRY once it is."*

That was the right call in the moment. It is now a launch-blocking hole that has been open for
five weeks because **nobody has been asked the question it is waiting on.**

**Blast radius.** An unauthenticated `PUT` or `DELETE` against
`https://calvary-scribblings-default-rtdb.europe-west1.firebasedatabase.app/top_stories.json`
empties the node, replaces it with arbitrary content, or writes unbounded data into billed
storage. There is **no in-repo reader** — grep across `app/`, `functions/`, `scripts/`,
`workers/` returns nothing — so an emptied node might not be noticed at all.

**What is actually needed is one answer, not one commit.** In descending order of preference:

1. **Identify the scheduled writer.** If it holds a service-account credential, it bypasses rules
   entirely and `".write": false` is safe today, with no coordination. That is the likely case and
   it takes one look at whatever runs the job.
2. If it writes as an anonymous or ordinary client, scope the grant to the exact path it writes
   (`top_stories/weekly`) and validate the shape, leaving the rest of the node closed.
3. If nothing writes it any more, `".write": false` — or delete the node.

**This is the same question as §3 below.** One conversation with whoever runs the Cloudflare
Workers answers both.

**When you fix it:** delete the `top_stories` entry from `DELIBERATELY_OPEN` in
`tests/rules/structure.test.mjs` — the suite has a test that fails if a blessed exception is no
longer open, so a stale entry cannot be left behind.

## §2 — THE PRE-LAUNCH SIX, RESTATED

All six were handed over in R9.0. Status: **none actioned.** Line numbers re-verified at

### PH2-2 · Roughly thirty writable nodes have no `.validate` — was P-PL-1

**Progress since handover 1: 13 of ~34 closed.** `f8f547d` and `39b908c` gave validators to
`followers`, `following`, `square_posts`, `square_likes`, `square_reactions`, `square_presence`,
`notifications`, `library_notifications`, `dm_conversations` and `dm_messages`; `wallet` and
`payout_requests` went to `".write": false`, so the question no longer arises for them; `stories`
likewise.

**Still carrying a write grant with no shape, type or length constraint anywhere beneath (20):**

`top_stories` (see PH2-1) · `user_search/$uid` · `user_square_posts/$uid` · `points` ·
`leaderboard/$uid` · `userBadges/$uid` · `userStreaks/$uid` · `userStoryTiers/$uid` ·
`quiz_submissions/$uid` · `storyReactions/$slug/$type` · `storyReactionUsers` ·
`commentReactions` · `comment_reactions` · `bookmarks` · `readerBookmarks` · `userProgress` ·
`userBookmarks` · `blocked_users` · `user_open_pages/$uid` · `open_pages_reactions` ·
`exercise_submissions/$uid`

Each is an unbounded write into billed Firebase storage by whoever holds the grant, and a
rendering hazard wherever another user's client reads it.

**Fix:** the `subscribers` pattern at `database.rules.json:135-155` — enumerate the fields,
type and bound each, and close the node with `"$other": { ".validate": false }`.
**Prioritise the ones another user's client renders:** `user_search` (the people search),
`user_square_posts`, `open_pages_reactions`.

**New:** write the probe first. `tests/rules/database.test.mjs` is the file, the four-case
template is at its head, and `npm run test:rules` runs it in ~20s with no credential.

### PH2-3 · Three stale Next route handlers with a hardcoded secret — was P-PL-2

`app/api/points-reset/route.js:5`
```js
const SECRET = 'calvary-points-reset-2026';
```
guards a `POST` that rewrites every node under `points` (`:17-30`). Two siblings:
`app/api/square-cleanup/route.js` and `app/api/points-reset/square-cleanup/route.js` — the nested
one looks like an accident of file placement.

**These do not deploy today.** Re-verified at `a4b300f`: `npx next build` exits 0 and `out/api`
does not exist, because `next.config.mjs` sets `output: 'export'`, which drops route handlers.
`CLAUDE.md` already names two of the three as stale.

**Risk:** zero today; total the day anyone changes `output` in `next.config.mjs` — three
unauthenticated destructive endpoints go live in the same commit. The secret is in git history
and editing the file cannot un-publish it.

**Fix:** `git rm -r app/api/points-reset app/api/square-cleanup`, then `npx next build` to
confirm nothing referenced them. If the monthly points reset is still wanted it belongs in
`functions/api/` behind a real credential. **One command.**

### PH2-4 · `open_pages` read counts are writable by any signed-in user — was P-PL-3

`database.rules.json:495-497`
```json
"readCount": { ".write": "auth != null && newData.isNumber()" }
```
on a node whose parent is otherwise carefully author-scoped (`:492-494`). Any account can set any
Open Pages post's public read count to any number. Cosmetic, but it is a public number the
platform presents as measurement.

**Fix:** move the counter behind `functions/api/hit.js`, which already mints an admin token, and
set the rule to `false`. The endpoint is already the pattern for exactly this.

### PH2-5 · `film_submissions` accepts unauthenticated RTDB creates — was P-PL-4

**Half of this is now fixed and half is not, which is worse than either.**

`storage.rules:103-108` — **CLOSED** by `f8f547d`. `allow write` now opens with
`request.auth != null`, and `tests/rules/storage.test.mjs` asserts it four ways.

`database.rules.json:49-55` — **STILL OPEN:**
```json
"film_submissions": {
  ".read": "auth != null && (founder || founder)",
  "$id": {
    ".write": "!data.exists()",
    ".validate": "newData.hasChildren(['type', 'name', 'email', 'createdAt'])"
  }
}
```
No `auth` term. Deletes are blocked (a delete needs `data.exists()` to be false, and it is not)
and the shape is required, so this is bounded — but it is unlimited anonymous creates into a
founder-read node.

**Why the split matters:** the two halves are one flow. A submission is an RTDB record plus a
PDF. Closing the upload and leaving the record open means an anonymous caller can still fill the
submissions list with entries that have no file behind them, and the founder reading that list
now has to tell real submissions from noise.

**Fix:** either add `auth != null` to match Storage, or — if anonymous film submission is
genuinely wanted — gate the Storage rule on a matching `film_submissions/$id` RTDB record created
in the same flow, and say so in a comment. Decide which, because the current state is neither.

### PH2-6 · `app/admin/page.js.bak` is tracked in git — was P-PL-8

`git ls-files | grep -E '\.(bak|old|orig)$'` → `app/admin/page.js.bak`, carrying the Firebase web
config at `:6`. Not built (`pageExtensions` in `next.config.mjs:8` excludes `bak`), so it does not
ship — but it is a live grep and fuzzy-open trap of exactly the kind `CLAUDE.md` was rewritten to
warn about, and an edit landing in it is silently lost.

**Fix:** `git rm app/admin/page.js.bak`. **One command.** The config it carries is the public web
config and is not a secret; the problem is the file, not its contents.

### PH2-7 · 146 lint errors in first-party code — was P-PL-7

`npx eslint app functions scripts tests` → **256 problems (146 errors, 110 warnings)**. The audit
said 184; the difference is R8.3's work, not anyone fixing lint. The dominant class remains
`react-hooks/set-state-in-effect` (cascading renders). Repo-wide the number is ~1100, but ~800 of
those are in the vendored `public/vendor/foliate-js-main` tree and are not ours.

**The ratchet the handover asked for now exists.** `scripts/lint-ratchet.mjs` runs in CI's
`hygiene` job and gates on the **direction**: the count may fall and may never rise.
`scripts/lint-baseline.json` holds `{errors: 146, warnings: 110}`. If you genuinely lower the
count, run `npm run lint:ratchet -- --update` and commit the baseline in the same change.

**Fix:** ordinary maintenance, worked down file by file. The worst are `app/square/page.js` (27),
`app/terms/page.js` (20), `app/privacy/page.js` (14), `app/profile/page.js` (13). No deadline
attached — the ratchet means it cannot get worse while you get to it.

## §3 — ONE QUESTION, TWO NODES

Both PH2-1 (`top_stories`) and the R9.2 waitlist finding are blocked on the same unanswered
question, and it is not a code question.

**Something outside this repository writes to this database.** Two pieces of evidence:

1. `top_stories/weekly` is regenerated on a schedule by a job that is in no file in this tree.
2. `bookstore_waitlist` holds **nine uid-keyed rows carrying only `{joinedAt}`**. The only
   in-repo writer of that node is `app/bookstore/components/LaunchGate.js:292`, which pushes
   `{email, addedAt}` under a push id — a different key shape and a different field set. An
   exhaustive search (every ref, every branch, the vestigial directories, `workers/`) found no
   writer of the uid-keyed shape anywhere.

**The candidates**, all Cloudflare Workers this tree references by URL but does not contain:

| worker | why it is or is not a candidate |
|---|---|
| `calvary-auth` | **most likely.** An auth Worker has a **uid** at hand, which is the one thing needed to write a uid-keyed row, and `joinedAt` is what you record when someone joins |
| `calvary-beta-signup` | `public/beta.html:471` posts to it. A signup form has an email, not a uid — so it fits the node and not the key shape |
| `calvary-age-verify`, `calvary-newsletter`, `calvary-og-image` | no obvious fit |

**What is needed:** whoever owns those Workers says what each writes to RTDB. That single answer
lets `top_stories` be closed properly rather than blindly, and identifies the nine rows so they
can be kept or removed on purpose.

**Do not delete the nine rows.** They are safe where they are: `bookstore_waitlist/$entry` is
create-only as of R9.1, so nothing client-side can alter or delete them, and
`tests/rules/database.test.mjs:512-521` asserts exactly that. They are also potentially real
people who asked to hear from us.

## §4 — WHAT THE BOOKSTORE CHANGED IN SHARED FILES, R9.2

Stated so it is not archaeology later. Nothing here is platform-owned; all of it is in shared
files you also touch.

- **`database.rules.json`** — two edits, both under `bookstore_*`, both deployed with
  `rules:check` parity proven before and after:
  - `bookstore_titles/$titleId`: `territoriesAllowed` tightened from `isString() || hasChildren()`
    to *exactly `'*'`, or a list of `/^[A-Z]{2}$/`*; `territoriesExcluded` validated for the first
    time. Pure tightening, 8 emulator probes.
  - `bookstore_purchases/$uid`: dead `.indexOn` removed. No permission change.
- **`.github/workflows/*.yml`** — action majors moved off the deprecated `node20` runtime.
  `checkout@v5`, `setup-node@v5`, `setup-java@v5`, **`upload-artifact@v6`**. The asymmetry is
  deliberate and load-bearing: `upload-artifact@v5` still declares `runs.using: node20` despite
  its release notes. Read `runs.using` from an action's own `action.yml` before changing any of
  them — `tests/ci/workflows.test.mjs` holds the floors and will tell you if you go under one.
  The hygiene job's trigger path widened to `.github/workflows/**`.
- **`package.json`** — one new script, `test:ci`, wired into the hygiene job.

Nothing else in a shared file was touched, and no platform-owned file was touched at all.
