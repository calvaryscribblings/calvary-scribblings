### The one thing to understand about Firebase RTDB rules before you start

Two behaviours drive most of what follows, and both are easy to get wrong:

1. **A `.write` grant at a node's root permits writing `null` to the entire subtree.** So
   `"followers": { ".write": "auth != null" }` does not mean "a signed-in user may add a
   follower" — it means "a signed-in user may delete every follower relationship in the product,
   in one request."
2. **`.validate` rules do not run on deletes**, and a `.validate` on a child does not constrain a
   write aimed at its parent. Careful per-field validators sitting under a permissive root grant
   protect nothing against wholesale replacement.

The rules file already contains four nodes that get this exactly right —
`subscribers` (`database.rules.json:135-155`), `leaderboards` (`:107-130`),
`bookstore_reading_progress` (`:486-497`) and `open_pages_pending` (`:354-378`). Each puts the
grant at the leaf, validates every field, and closes the shape with
`"$other": { ".validate": false }`. **That is the pattern to copy. It is already house style; it
simply was never applied to the older nodes.**

## LAUNCH-BLOCKING (9)

### P-LB-1 · `stories` and `top_stories` are writable by anyone on the internet, with no account

**File:** `database.rules.json:8-15`
```json
"stories":     { ".read": true, ".write": true },
"top_stories": { ".read": true, ".write": true }
```

No `auth` clause. No `.validate`. No size bound. These are the only two nodes in the entire file
with an **unauthenticated** write grant.

**What can happen:** an unauthenticated `PUT` or `DELETE` to
`https://calvary-scribblings-default-rtdb.europe-west1.firebasedatabase.app/stories.json` empties
the node, replaces it with arbitrary content, or writes unbounded data into billed storage.

**Who reads them:** `stories` is read at `app/inspiring/page.js:73` —
`const hitsSnap = await get(ref(db, 'stories'))` — and whatever comes back feeds that page.
`top_stories` has **no reader anywhere** in `app/`, `functions/`, `scripts/` or `workers/`.

**Fix:** set both to `".write": false`. Neither has an in-repo writer, so nothing should break;
confirm `app/inspiring/page.js:73` still resolves and consider deleting `top_stories` outright.

### P-LB-2 · Every private direct message is readable — and deletable — by every signed-in user

**File:** `database.rules.json:237-240`
```json
"dm_messages": { ".read": "auth != null", ".write": "auth != null" }
```

Both rules sit at the **root of the node**, not under a conversation id.

**Where the data comes from:** `app/square/page.js:463` and `:488` read
`dm_messages/${convId}`; `:540` pushes new messages there. These are real private conversations
between real users.

**What can happen:** `GET /dm_messages.json` with any account's token returns **every private
message ever sent between any two users in the product**. `DELETE /dm_messages.json` destroys all
of them. This is a personal-data breach of a kind that is reportable, and it is one HTTP request.

**Fix:** move both rules down under `$convId` and gate on membership of that conversation. The
membership index already exists — `dm_conversations/$uid` (`:231-236`) records which conversations
a user is in — so the rule has something to check against.

**Treat this as the highest-priority item in this document.** It is the only finding here that is
a privacy breach rather than an integrity or availability problem.

### P-LB-3 · Any signed-in user can set any other user's wallet balance

**File:** `database.rules.json:251-256`
```json
"wallet": {
  "$uid": {
    ".read":  "$uid === auth.uid",     ← correctly owner-scoped
    ".write": "auth != null"           ← not scoped at all
  }
}
```

The read rule got it right and the write rule did not. `app/profile/page.js:578` reads
`wallet/${u.uid}/balance` and renders it to the user as their money.

**What can happen:** any account can set any other account's balance to any number, or zero it.

**Fix:** `".write": "auth != null && auth.uid === $uid"` at minimum. If these balances ever back a
real payout, they should be written server-side only — from a Pages Function holding an admin
token, or restricted to the founder UIDs.

### P-LB-4 · Any signed-in user can file a payout request in someone else's name

**File:** `database.rules.json:257-263`
```json
"payout_requests": {
  ".read": "auth != null && (founder || founder)",
  "$uid": {
    ".read":  "$uid === auth.uid || founder || founder",
    ".write": "auth != null"           ← anyone, under any uid
  }
}
```

This is already known internally. `app/admin/analytics/page.js:90` carries the note:

> `payouts: 'DORMANT: no in-repo writer for payout_requests; payouts are not yet enabled. Node is
> also open-write — treat as a stub.'`

**What can happen:** the node an operator will one day read to decide who gets paid can be
populated by anyone, under anyone's uid, **before it is ever wired up**. A dormant node that is
open-write is a ledger that arrives pre-poisoned.

**Fix:** `".write": false` today. When a real writer exists, make it server-side.

### P-LB-5 · Six shared nodes can be wiped by one request from any account

**File:** `database.rules.json`

| node | lines | rule |
|---|---|---|
| `followers` | 189-192 | `".read": true, ".write": "auth != null"` |
| `following` | 193-196 | `".read": true, ".write": "auth != null"` |
| `square_posts` | 197-200 | `".read": true, ".write": "auth != null"` |
| `square_likes` | 201-204 | `".read": true, ".write": "auth != null"` |
| `square_reactions` | 205-208 | `".read": true, ".write": "auth != null"` |
| `square_presence` | 209-212 | `".read": true, ".write": "auth != null"` |

In all six the `.write` is on the **node root** — see the primer above: that grant covers writing
`null` to the whole subtree.

**Who reads them:** `app/components/OpenPagesProfileSection.jsx:68` counts `followers/$uid`;
`app/square/page.js:830` writes and `:846` subscribes to `square_presence`.

**What can happen:** one `DELETE` from any account destroys the entire social graph, or the whole
Square feed, or every like in the product. None of the six has a `.validate` anywhere beneath it,
so the same grant also permits writing unbounded data into billed storage.

**Fix:** move each `.write` down one level — to `$uid` for `followers`/`following`/
`square_presence`, to `$postId` for the rest — and scope it to the owner. **As a general rule
coming out of this audit: no node should carry a `.write` at its own root unless wholesale
replacement by that principal is genuinely intended.**

### P-LB-6 · Firebase Storage accepts unauthenticated 25 MB uploads to caller-chosen paths

**File:** `storage.rules:94-98`
```
match /film_submissions/{submissionId}/{fileName} {
  allow read: if request.auth != null && (founder || founder);
  allow write: if request.resource.size < 25 * 1024 * 1024
               && request.resource.contentType == 'application/pdf';
}
```

The `write` clause has **no `request.auth` term**, and both `{submissionId}` and `{fileName}` are
chosen by the caller. This is the only rule in the file without an auth check — every other
`write` in `storage.rules` names a specific uid or the two founder UIDs.

**What can happen:** anyone can upload unlimited 25 MB PDFs into the billed bucket at paths of
their choosing, and can overwrite a genuine submission before an operator reads it. Read is
admin-only, so this is a cost and integrity problem rather than a disclosure one — but it is
completely unmetered.

**Fix:** add `request.auth != null`. If anonymous submission is a deliberate product decision,
gate the upload on a matching RTDB record created in the same flow — and see P-PL-4, which is the
RTDB half of the same surface.

### P-LB-7 · Three notification nodes accept writes into any user's inbox

**File:** `database.rules.json:219-236`
```json
"notifications":         { "$uid": { ".read": "auth != null && auth.uid == $uid", ".write": "auth != null" } },
"library_notifications": { "$uid": { ".read": "auth != null && auth.uid == $uid", ".write": "auth != null" } },
"dm_conversations":      { "$uid": { ".read": "auth != null && auth.uid == $uid", ".write": "auth != null" } }
```

Read is correctly owner-scoped in all three. Write is scoped to *"is signed in"*, not *"is
`$uid`"*, and none of them has a `.validate`.

**Why this one is worse than it looks:** this is a node **one user writes and another user's
client reads and renders**. Any account can inject arbitrary content — arbitrary text, arbitrary
claimed sender, arbitrary fields — into any reader's notification tray or conversation list, or
wipe it.

**Fix:** notifications are legitimately written by third parties, so `auth.uid == $uid` is the
wrong rule. Add a `.validate` that pins the shape, caps every string length, requires a
`fromUid` equal to `auth.uid`, and closes the object with `"$other": { ".validate": false }` —
the `open_pages_pending` block at `:354-378` is a working example of exactly this shape.

### P-LB-8 · Any signed-in user can delete any other user's handle

**File:** `database.rules.json:164-169`
```json
"usernames": {
  ".read": true,
  "$handle": {
    ".write": "auth != null && (!data.exists() || data.val() === auth.uid || !newData.exists() || founder || founder)"
  }
}
```

The third disjunct — `!newData.exists()` — is true for **any delete**, by **anyone signed in**,
against **any handle**.

**What can happen:** handle hijack in two requests. Delete the victim's mapping (allowed by
`!newData.exists()`), then claim the freed handle (allowed by `!data.exists()`). `/u/:handle` is a
301 into `/user?handle=…` (`public/_redirects:15`), so every profile link the victim has ever
shared now resolves to the attacker.

**Fix:** delete the `!newData.exists()` clause. Removing a handle should require
`data.val() === auth.uid`, the same as every other operation on the node.

### P-LB-9 · Comment counters and reply threads are writable by any signed-in user

**File:** `database.rules.json:170-188`
```json
"comments": { "$slug": { "$commentId": {
  ".write": "auth != null && (!data.exists() || data.child('uid').val() === auth.uid || data.child('authorUid').val() === auth.uid)",
  ".validate": "newData.hasChildren(['text','authorName','authorUid','createdAt'])",
  "heartCount": { ".write": "auth != null" },   ← no owner check, no validate
  "fireCount":  { ".write": "auth != null" },   ← no owner check, no validate
  "replies":    { ".write": "auth != null" }    ← no owner check, no validate, whole subtree
}}}
```

The comment body itself is properly guarded. The three child rules then **widen** it — a `.write`
on a child overrides the parent for that path — and none of the three carries a `.validate`.

**What can happen:** `replies` is an unvalidated write grant over an entire subtree that every
reader of that story renders. Any account can inject arbitrary reply objects, with any
`authorName` and any `authorUid`, under anyone's comment. `heartCount` and `fireCount` can be set
to any value, including non-numbers.

**Fix:** give `heartCount`/`fireCount` a `.validate: "newData.isNumber()"`, and better, move the
counters to a per-uid child node — `comment_likes` at `:398-425` already does exactly this and is
the in-repo model. Give `replies` a `$replyId/$uid` owner-scoped structure to match.

## NOTES (6) — recorded so they are not rediscovered

1. **`app/admin/analytics/page.js:90` now lies.** It says *"`points/{uid}` is writable by any
   signed in user (no owner check)"*. Commit `67354b0` added the owner check;
   `database.rules.json:245` now reads `auth.uid === $uid || founder`. The caveat should say
   *self*-writable, not *world*-writable — see P-OCT-1, which is the part still true.
2. **`public/_redirects` is generated but git-tracked.** `public/_redirects:1-2` says *"Auto-
   generated … Do not edit by hand"*, and `scripts/generate-redirects.mjs` rewrites it on every
   build. It currently shows 14 uncommitted insertions purely because a build ran. Every local
   build dirties the tree, so `git status` stops being a signal. **Either gitignore it or commit
   it deliberately as part of a publish step.**
3. **The build depends on a live, unauthenticated Firebase read.** `npm run build` runs
   `generate-redirects.mjs` and `generate-gateway-wall.mjs` before `next build`; both `fetch`
   `cms_stories.json` from production (`:49` and `:66`), and the wall generator then fetches every
   cover URL stored in the database (`generate-gateway-wall.mjs:84`). The redirects generator
   catches its failure and degrades silently to a `_redirects` file missing 154 story routes; the
