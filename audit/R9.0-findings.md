# R9.0 — PRE-LAUNCH HEALTH AUDIT

**Date:** 2026-08-03 · **Method:** R7.0 recon method at repo scale · **Mode:** read-only
**HEAD at audit:** `02a36ab` (R8.2.1: grant events can never resurrect a revoked purchase)
**Store opens:** 2026-09-30 — eight weeks out.

Every finding carries an ID, a severity, an owner, evidence (file:line or command output), a
one-sentence blast radius and a one-sentence remedy. Nothing here was fixed; nothing was
deployed; no external system was written to. Live reads of our own public REST surface and of
the npm registry were performed and are labelled where used.

Severities:

| | |
|---|---|
| **LAUNCH-BLOCKING** | Money, private data or an irreplaceable asset is at risk today. Fix before the store takes a real card. |
| **PRE-LAUNCH** | Wrong or fragile in a way a paying customer will meet. Fix before 30 September. |
| **OCTOBER** | Real, bounded, and survivable through launch. |
| **NOTE** | Recorded so it is not rediscovered. No action implied. |

Counts: **13 LAUNCH-BLOCKING · 21 PRE-LAUNCH · 8 OCTOBER · 12 NOTE** — 54 findings.
By owner: **platform 25 · bookstore 20 · shared 7 · gateway 2 · app 0**.

## §0 — THE FIVE-LINE VERSION

1. The **reader** is hardened. Almost nothing else is, and the gap is not subtle.
2. **`database.rules.json` is the single largest exposure in the repo.** Two nodes are writable
   by anyone on the internet with no account at all; six more are wipeable in one request by any
   signed-in user; every private direct message in the product is readable by any signed-in
   user. None of this is bookstore code and none of it is new — it has simply never been read
   line by line before.
3. The **money path is well-built and narrowly wrong in one place**: grants were hardened in
   R8.2.1 and revocations were not. A refund can take away a book the reader has since re-bought,
   and My Library shows revoked books as owned.
4. **Nothing outside the reader and the bookstore is defended by CI** — not the rules, not the
   service worker, not the newsletter, not lint, not `npm audit`.
5. **No outbound fetch anywhere in `functions/` has a timeout.** Thirteen of them are on the
   money path.

## §1 — LAUNCH-BLOCKING (13)

Ranked by blast radius across all owners. Owner is in the header.

### LB-1 · `stories` and `top_stories` are writable by anyone on the internet — platform

**Evidence** — `database.rules.json:8-15`
```json
"stories":     { ".read": true, ".write": true },
"top_stories": { ".read": true, ".write": true }
```
No `auth` clause, no `.validate`, no size bound. `stories` is read live by
`app/inspiring/page.js:73` (`get(ref(db, 'stories'))`). `top_stories` has **no in-repo reader at
all** — grep across `app/`, `functions/`, `scripts/`, `workers/` returns nothing.

**Blast radius** — an unauthenticated `PUT`/`DELETE` against
`https://calvary-scribblings-default-rtdb.europe-west1.firebasedatabase.app/stories.json` can
empty the node, replace it with arbitrary content that `app/inspiring/page.js` then renders, or
write unbounded data into the project's billed storage.

**Remedy** — set both to `".write": false` (neither has an in-repo writer) and confirm
`app/inspiring/page.js:73` still resolves, or delete the nodes outright.

### LB-2 · Every private direct message is readable by every signed-in user — platform

**Evidence** — `database.rules.json:237-240`
```json
"dm_messages": { ".read": "auth != null", ".write": "auth != null" }
```
The rule is at the **root of the node**, not under `$convId`. `app/square/page.js:463,488,540`
reads and writes `dm_messages/${convId}`, so real conversations live here.

**Blast radius** — any account (signup is open) can `GET /dm_messages.json` and read every
private message ever sent between any two users, and can `DELETE /dm_messages.json` to destroy
all of them. This is a personal-data breach of the kind that is reportable, and it is one HTTP
request.

**Remedy** — move both rules under `$convId` and gate on conversation membership (the
`dm_conversations/$uid` index already records who is in which conversation).

### LB-5 · Six shared nodes can be wiped wholesale by one request from any account — platform

**Evidence** — `database.rules.json`
| node | line | rule |
|---|---|---|
| `followers` | 189-192 | `".read": true, ".write": "auth != null"` |
| `following` | 193-196 | `".read": true, ".write": "auth != null"` |
| `square_posts` | 197-200 | `".read": true, ".write": "auth != null"` |
| `square_likes` | 201-204 | `".read": true, ".write": "auth != null"` |
| `square_reactions` | 205-208 | `".read": true, ".write": "auth != null"` |
| `square_presence` | 209-212 | `".read": true, ".write": "auth != null"` |

In every case `.write` sits on the **node root**, so the grant covers a write of `null` to the
whole subtree. Consumers: `app/components/OpenPagesProfileSection.jsx:68` (`followers/$uid`),
`app/square/page.js:830,846` (`square_presence`).

**Blast radius** — one `DELETE` from any account destroys the entire social graph, the whole
Square feed, or every like in the product. There is no `.validate` anywhere in the six, so the
same grant also permits writing unbounded data into billed storage.

**Remedy** — move each `.write` down one level to `$uid` / `$postId` and scope it to the owner;
no node should carry a `.write` at its own root unless a wholesale replacement is intended.

### LB-6 · Storage accepts unauthenticated 25 MB uploads to arbitrary paths — platform

**Evidence** — `storage.rules:94-98`
```
match /film_submissions/{submissionId}/{fileName} {
  allow read: if request.auth != null && (founder || founder);
  allow write: if request.resource.size < 25 * 1024 * 1024
               && request.resource.contentType == 'application/pdf';
}
```
The `write` clause has **no `request.auth` term**. `{submissionId}` and `{fileName}` are
caller-chosen. This is the only rule in the file without an auth check — every other `write` in
`storage.rules` names a uid or the two founder UIDs.

**Blast radius** — anyone can upload unlimited 25 MB PDFs into the project's billed bucket at
paths of their choosing, and can overwrite a genuine submission before it is read. Read is
admin-only, so this is a cost and integrity problem rather than a disclosure one — but it is
unmetered.

**Remedy** — add `request.auth != null` and, if anonymous submission is genuinely wanted, gate on
a matching `film_submissions/$id` RTDB record created in the same flow.

### LB-7 · A refund can take away a book the reader has already re-bought — bookstore

**Evidence** — `functions/api/bookstore/stripe-webhook.js:213-227` and
`functions/api/bookstore/paystack-webhook.js:274-288`
```js
async function handleRevoke(env, obj, reason) {
  const { uid, titleId } = extractIdentity(obj);
  if (!uid || !titleId) { …return; }
  const token = await mintAccessToken(…);
  await patchPurchase(env, token, uid, titleId, buildRevokePayload(reason));   // ← unconditional
}
```
There is no equivalent of `shouldSkipGrant()` on this path. `functions/api/bookstore/_lib.js:346`
`buildRevokePayload()` writes `status:'revoked'` with no reference field, and
`_lib.js:386-390` `shouldSkipGrant()` — the guard R8.2.1 built — is called **only** from the two
grant handlers (`stripe-webhook.js:188`, `paystack-webhook.js:250`).

**The sequence** (both rails, same shape):
1. Reader buys → session `A` → `{stripeSessionId:'A', status:'active'}`.
2. Reader refunds → `charge.refunded` for `A` → `{status:'revoked'}`.
3. Reader buys again → session `B` → `{stripeSessionId:'B', status:'active'}`. Correct, and
   `_lib.js:355-385` documents this repurchase path as proven on glass.
4. `charge.dispute.created` (or a late `refund.processed`) arrives **for the original charge
   `A`** — Stripe raises disputes days after a charge, Paystack retries for 72 hours — and step 3
   is silently reverted.

The grant side is asymmetrically correct: `_lib.js:378-385` explains at length why status must
play no part in the grant decision and why the reference alone decides. The same argument was
never applied to revocation.

**Blast radius** — a reader who paid twice ends up owning nothing, with no log line that reads as
an error (`stripe-webhook.js:226` logs the revocation as a success). Money and grants disagree,
and the disagreement is invisible.

**Remedy** — carry the transaction reference into `buildRevokePayload()` and refuse the write
when the stored record names a *different, later* transaction — the mirror image of
`shouldSkipGrant()`.

### LB-8 · My Library shows revoked books as owned — bookstore

**Evidence** — `app/my-library/page.js:220-254`
```js
const snap = await get(ref(db, `bookstore_purchases/${user.uid}`));
if (!snap.exists()) { … }
const entries = [];
snap.forEach((child) => { entries.push({ id: child.key, ...(child.val() || {}) }); return false; });
```
Every child is taken. **`status` is never read.** The resolved object at `:239-246` projects
`slug`, `title`, `author`, `coverUrl`, `purchasedAt` and drops `status` entirely. `BookCard`
(`:74-87`) then renders an unconditional `<a className="ml-read" href={/reader/${book.slug}}>READ
NOW</a>`.

By contrast `functions/api/bookstore/stream.js:110-115` is strict:
```js
if (purchase.status !== 'active') return json({ …, code: 'revoked' }, 403);
```

**Blast radius** — a refunded, disputed or charged-back reader keeps seeing the book on their
shelf with a live READ NOW that 403s. The bytes are safe; the shelf lies. Combined with LB-7 this
is the visible face of a purchase the reader believes they own.

The header comment at `app/my-library/page.js:11-14` explains why this was never caught: *"Since
the Book Store doesn't open until 30 September 2026 there are no purchases yet, so the countdown
IS the empty state."* That stops being true on launch day.

**Remedy** — filter `entries` to `p.status === 'active'` (matching `stream.js:110`) and decide
deliberately whether a revoked row should be hidden or shown with an honest label.

### LB-9 · The launch mailing list can be deleted by anyone, unauthenticated — bookstore

**Evidence** — `database.rules.json:499-513`
```json
"bookstore_waitlist": {
  ".read": "auth != null && (founder || founder)",
  ".write": true,                                    ← node root, no auth
  "$entry": { ".validate": "newData.hasChildren(['email','addedAt'])", … }
}
```
The `$entry` validators are careful and well-matched to `isEmailShaped()` in
`app/lib/bookstore/gate.js:93-99`. They are also irrelevant to the exposure: `.validate` does not
run on a delete, and the `.write` grant sits above them at the node root.

`app/lib/bookstore/gate.js:114-115` is explicit about what this node is worth: *"What R9 does NOT
delete: the bookstore_waitlist node, its rules, or the addresses in it. Those are a mailing list
that outlives the curtain and is the reason it existed."*

**Not executed** — this was derived from rule semantics, not tested. Testing it would have
destroyed the asset.

**Blast radius** — a single unauthenticated `DELETE
/bookstore_waitlist.json` erases every address gathered behind the curtain since R8.1. There is
no backup step anywhere in the repo.

**Remedy** — move `.write` to `$entry` and require `!data.exists()` (append-only), matching the
shape `subscribers` already uses at `database.rules.json:137-138`; and snapshot the node before
launch.

### LB-10 · No outbound fetch in `functions/` has a timeout — bookstore

**Evidence** — `grep -rn "AbortSignal\|AbortController\|signal:" functions/` → **no matches.**
Thirteen unguarded calls on the money path:

|---|---|

| `_lib.js:145` | `oauth2.googleapis.com/token` — every admin-token mint |
| `_lib.js:276` | RTDB `GET` purchase (idempotency read) |
| `_lib.js:286` | RTDB `PATCH` purchase (**the grant write**) |
| `_lib.js:300` | RTDB `GET` title record |
| `checkout.js:86` | RTDB `GET` title |
| `checkout.js:104` | RTDB `GET` publisher |
| `checkout.js:156` | `api.stripe.com/v1/checkout/sessions` |

### LB-11 · Three notifications nodes accept writes into any user's inbox — platform

**Evidence** — `database.rules.json:219-236`
```json
"notifications":         { "$uid": { ".read": "auth != null && auth.uid == $uid", ".write": "auth != null" } },
"library_notifications": { "$uid": { ".read": "auth != null && auth.uid == $uid", ".write": "auth != null" } },
"dm_conversations":      { "$uid": { ".read": "auth != null && auth.uid == $uid", ".write": "auth != null" } }
```
Read is correctly owner-scoped in all three. Write is scoped to *"is signed in"*, not *"is
$uid"*, and there is no `.validate` on any of them.

**Blast radius** — this is the textbook injection surface the audit brief asked for: a node one
user writes and **another user's client reads and renders**. Any account can inject arbitrary
content into any reader's notification tray or conversation list, or wipe it.

**Remedy** — notifications are inherently written by a third party, so the owner check cannot
simply be `auth.uid == $uid`; add a `.validate` that pins shape and length and records
`fromUid === auth.uid`, and cap writes to fields the sender is allowed to set.

### LB-12 · Any signed-in user can delete any other user's handle — platform

**Evidence** — `database.rules.json:164-169`
```json
"usernames": {
  ".read": true,
  "$handle": {
    ".write": "auth != null && (!data.exists() || data.val() === auth.uid || !newData.exists() || founder || founder)"
  }
}
```
The third disjunct, `!newData.exists()`, is true for **any delete**, by **anyone signed in**,
against **any handle**.

**Blast radius** — handle hijack in two requests: delete the victim's mapping, then claim it via
the `!data.exists()` branch. `/u/:handle` is a 301 into `/user?handle=` (`public/_redirects:15`),
so the victim's shared profile links resolve to the attacker.

**Remedy** — drop `!newData.exists()`; deletion should require `data.val() === auth.uid` like
every other operation on the node.

### LB-13 · Comment counters and reply threads are writable by any signed-in user — platform

**Evidence** — `database.rules.json:170-188`
```json
"comments": { "$slug": { "$commentId": {
  ".write": "auth != null && (!data.exists() || data.child('uid').val() === auth.uid || data.child('authorUid').val() === auth.uid)",
  ".validate": "newData.hasChildren(['text','authorName','authorUid','createdAt'])",
  "heartCount": { ".write": "auth != null" },      ← no validate, no owner check
  "fireCount":  { ".write": "auth != null" },      ← no validate, no owner check
  "replies":    { ".write": "auth != null" }       ← no validate, no owner check, whole subtree
}}}
```
The comment body itself is properly guarded. The three child rules **widen** it: a `.write` on a
child overrides the parent for that path, and none of the three carries a `.validate`.

**Blast radius** — `replies` is an unvalidated write grant over an entire subtree that every
reader of that story renders. Any account can inject arbitrary reply objects — with any
`authorName` and any `authorUid` — under anyone's comment, and set the visible heart/fire counts
to anything.

**Remedy** — give `heartCount`/`fireCount` a `.validate: "newData.isNumber()"` and move the
counter to a per-uid child node the way `comment_likes` (`:398-425`) already does; give `replies`
the same `$replyId` owner-scoping as its sibling.

## §2 — PRE-LAUNCH (21)

### PL-1 · A revocation for a purchase that never existed creates a phantom record — bookstore
`stripe-webhook.js:225` / `paystack-webhook.js:286` call `patchPurchase()`, and `_lib.js:285-292`
uses `PATCH`, which **creates** the node when it is absent. A refund or dispute event whose
`uid`/`titleId` do not match a real purchase writes `{status:'revoked', revokedAt, revokedReason}`
into `bookstore_purchases/{uid}/{titleId}` with no `purchasedAt`. With LB-8 unfixed that renders
on the reader's shelf as a book titled `'Untitled'` (`app/my-library/page.js:242`).
**Remedy** — read before revoking; log and return when nothing is there.

### PL-2 · The Paystack rail has no client caller — bookstore
`grep -rn "api/bookstore" app/` returns `/api/bookstore/stream` (`app/lib/bookstore/stream.js:36`)
and `/api/bookstore/checkout` (`app/lib/bookstore/checkout.js:26`) only. **Nothing in `app/` ever
posts to `/api/bookstore/paystack-checkout`.** `BuyButton.js:37` hardcodes
`createCheckoutSession(user, title?.id, 'gbp')`. The 214-line endpoint, its 341-line webhook and
their test suite are live and unreachable.
Confirmed against production (live public REST read, 2026-08-03): no published title carries an
NGN price — `basil`, `the-fire-in-the-flint`, `the-rescue` are `{"gbp":199}`; only the `draft`
title `test-drive` has `ngn`.
**Remedy** — decide before launch whether NGN ships (then wire a currency choice into
`BuyButton`) or does not (then say so in `paystack-checkout.js`'s header so the next reader does
not assume it is wired). **This is a decision for Ikenna, not a fix.**

### PL-3 · `checkout.session.completed` grants without checking `payment_status` — bookstore
`stripe-webhook.js:267` routes on event type alone; `handleGrant()` (`:155-211`) never inspects
`session.payment_status`. For card payments Stripe sets it to `paid`, so this is correct today.
For any delayed-payment method the same event fires with `unpaid`, and the book is granted before
the money exists. That the file maps `checkout.session.async_payment_failed` to a revocation
(`:68`) shows the async case was anticipated — but the grant still lands first.
**Remedy** — one line: `if (session.payment_status !== 'paid') return;` plus handling
`checkout.session.async_payment_succeeded`.

### PL-4 · `bookstore_purchases` declares an index on two fields that do not exist — bookstore
`database.rules.json:480-483` declares `".indexOn": ["purchaseDate","titleId"]`.
`_lib.js:335-344` `buildGrantPayload()` writes **`purchasedAt`**, not `purchaseDate`; and
`titleId` is the **record key** (`_lib.js:272-273`), not a field. No `orderByChild` anywhere in
the tree targets this node. The index is dead on both counts and costs write throughput.
**Remedy** — delete it, or correct it to `purchasedAt` if a shelf sort is planned.

### PL-5 · The launch gate is an overlay, not a dialog — bookstore (a11y)
`app/bookstore/components/LaunchGate.js:196-200` renders `<div className="bg-gate">` with
`position:fixed;inset:0;z-index:9000` (`:45-49`) and **no** `role="dialog"`, no `aria-modal`, no
`autoFocus`, no focus trap, and no `inert`/`aria-hidden` on the storefront. The storefront is a
**sibling slot in the same fragment**, mounted at all times — `app/bookstore/page.js:306-473`,
`app/bookstore/[slug]/page-detail.js:133-134`. Grep confirms: no `autoFocus`, `focus()`, `inert`,
`aria-modal` or `role="dialog"` in either file.
**Blast radius** — a keyboard or screen-reader user on `/bookstore` tabs through the navbar, the
tab bar and the entire storefront *behind* an opaque curtain before reaching the passcode field;
and when the curtain lifts, focus is on an unmounted button and falls to `<body>`.
**Remedy** — `role="dialog" aria-modal="true"`, focus the passcode input on mount, trap Tab
within `.bg-inner`, and move focus to the storefront heading in `onLifted`.

### PL-8 · Eighteen scripts depend on packages that are not in `package.json` — shared
`npm ls --depth=0` reports `firebase-admin@14.2.0`, `@google-cloud/firestore@8.7.0`,
`@google-cloud/storage@7.21.0`, `teeny-request`, `gcp-metadata` and ~20 more as **extraneous** —
present on this disk, absent from `package.json` and from `package-lock.json`.
Eighteen files import them, including operational machinery:
`scripts/rules-pull.mjs` (→ `npm run rules:check`, `npm run rules:deploy`),
`scripts/leaderboard-snapshot.mjs` (the Summer Reading snapshot),
`scripts/leaderboard-audit.mjs`, `scripts/compute-metrics.mjs`, and every `backfill-*` /
`repair-*` script.
`npm ci --dry-run` confirms the drift: *"added 31 packages, removed 84 packages, and changed 186
packages"*.
**Blast radius** — a fresh clone plus `npm ci` — which is exactly what CI does
(`.github/workflows/reader-tests.yml:76`) and roughly what Cloudflare Pages does — cannot run the
rules checker, the rules deploy, or the contest snapshot. This machine works because of state
nobody recorded.
**Remedy** — add `firebase-admin` to `devDependencies` and re-lock; the `@google-cloud/*`
packages come along as its transitive deps.

### PL-9 · CI defends the reader and the bookstore. Nothing else. — shared
`.github/workflows/reader-tests.yml` is the **only** workflow in the repo. Full coverage map in
§7 below. The naked cells, ranked:
1. **`database.rules.json` / `storage.rules`** — not in the trigger paths (`:31-49`), no test
   suite exists, and `npm run rules:check` is never invoked by CI. The file carrying LB-1 through

## §9 — WHAT NEEDS A DECISION FROM IKENNA, NOT A FIX FROM ANYONE

1. **Does the naira rail ship on 30 September?** (PL-2) It is fully built server-side, fully
   tested, and completely unreachable from the UI. No published title has an NGN price. Either
   wire a currency choice into `BuyButton.js` and price the three titles in naira, or mark the
   rail dormant in its own header. Leaving it as-is means a working payment rail nobody can use
   and a second webhook accepting live events.
2. **Are both providers going live, and when?** (NA-1, NA-7) The flip needs new keys, a new
   `STRIPE_WEBHOOK_SECRET`, and a re-check that `charge.refunded` and `charge.dispute.created`
   are subscribed. Without those two events, LB-7 becomes moot in the worst way: nothing revokes
   at all.
3. **Is `territoriesAllowed` meant to be enforced?** (NA-10) The rules require the field, the
   endpoints ignore it. Either wire it into both checkout endpoints or drop it from the schema —
   a required field nothing reads will be assumed to work by whoever ships the next surface.
4. **How much of the rules surface gets fixed before launch?** LB-1 through LB-5 and LB-11
   through LB-13 are all platform-owned and none of them is bookstore work. They are handed over
   in `audit/R9.0-platform-handover.md`. **The bookstore cannot fix them and should not wait on
   them** — but LB-9 (the waiting list) sits in the same file and *is* bookstore-owned.
5. **Is the Summer Reading leaderboard's self-writable score acceptable for the August close?**
   (OCT-2) The snapshot node is trustworthy; the live node is not. If the contest is decided from
   the snapshot, this is a non-issue and should be written down as such.
